1 Por que precisamos do conceito de "processo"?

Abra o gerenciador de tarefas do seu computador agora. Você vai ver dezenas de programas rodando ao mesmo tempo: navegador, editor de texto, música, antivírus, sistema operacional. Mas seu processador tem só alguns núcleos — talvez 4, talvez 8. Como 200 programas conseguem rodar em 4 núcleos?

A resposta curta: eles não rodam simultaneamente. O sistema operacional alterna entre eles tão rápido (milhares de vezes por segundo) que parece simultâneo. Mas para alternar, o SO precisa lembrar onde cada programa parou — qual instrução ele estava executando, quais valores tinha nos registradores, qual memória estava usando.

🍽️ Analogia: garçom servindo várias mesas

Sem o conceito de "comanda"

O garçom esquece quem pediu o quê assim que vira de costas. Caos — ninguém é servido corretamente.

📋 Com comanda por mesa

"Comanda" = processo

Cada mesa tem sua comanda com pedido, status (esperando, comendo, esperando conta), histórico. O garçom alterna entre mesas mas nunca se perde.

Um processo é exatamente isso: a "comanda" que o SO mantém para cada programa em execução. Toda vez que o SO interrompe um programa para rodar outro, ele atualiza a comanda — e quando volta a rodar aquele programa, lê a comanda para saber onde parou.

Insight central: "processo" é a unidade básica que o sistema operacional gerencia. Sem essa abstração, multitasking seria impossível. Tudo neste módulo é sobre como os processos são representados, criados, transitam entre estados e se comunicam.

O que faz parte do processo?

Antes de entrar no formal, pense no que o SO precisa lembrar para "retomar" um programa que foi pausado:

  • 1. Qual instrução vai ser executada a seguir. Sem isso, o programa não sabe onde continuar.
  • 2. Os valores dos registradores da CPU. Variáveis em uso no meio de um cálculo.
  • 3. A memória que o programa está usando. Variáveis, pilha de chamadas, dados.
  • 4. Quais arquivos estão abertos. Posição de leitura, modo de acesso.
  • 5. Em que estado está. Rodando? Esperando teclado? Esperando disco?

Cada um desses itens vai ganhar nome técnico nas próximas seções. Agora você já tem a intuição: processo é tudo aquilo que o SO precisa saber sobre um programa em execução para conseguir pausar e retomar sem perder nada.

→ Próximo passo (seção 2): antes de mergulhar na estrutura técnica, precisamos esclarecer uma confusão muito comum — qual a diferença entre programa (o que você baixa, instala) e processo (o que está rodando)?

2 Processo vs. programa — não são a mesma coisa

"Programa" e "processo" são frequentemente usados como sinônimos no dia a dia, mas em sistemas operacionais essa distinção é crítica e cai em prova.

📄 Programa

Receita de bolo

É o arquivo no disco. Estático. Inerte. Nunca executou nada. chrome.exe, python, ls.

⚡ Processo

Bolo sendo feito agora

É a execução do programa. Dinâmico. Tem estado em mudança. Consome CPU e memória agora.

Implicação importante: o mesmo programa pode dar origem a vários processos rodando ao mesmo tempo. Você pode abrir três janelas do navegador — três processos do mesmo programa chrome.exe. Eles não compartilham memória, têm PIDs diferentes, podem estar em estados diferentes.

Exemplo concreto

Você executa python script.py três vezes em três terminais. Resultado:

  • 1 programa: /usr/bin/python (mesmo arquivo binário no disco)
  • 1 script: script.py (mesmo código sendo executado)
  • 3 processos: cada um com PID distinto, memória própria, conjunto de variáveis independente

Se um processo trava, os outros dois continuam rodando — eles são totalmente isolados.

Anatomia do espaço de endereçamento de um processo

Quando o SO carrega um programa para a memória e cria o processo, ele organiza essa memória em regiões. Saber essa organização é fundamental — em F5.3 Memória Virtual vamos detalhar cada uma.

ENDEREÇOS ALTOS ↑
Stack — variáveis locais, parâmetros de função, endereço de retorno. Cresce ↓
(espaço livre no meio)
Heap — memória alocada dinamicamente (malloc, new). Cresce ↑
Data — variáveis globais e estáticas (int counter = 0)
Text (Code) — instruções do programa. Read-only, compartilhável.
ENDEREÇOS BAIXOS ↓

Stack e Heap crescem em direções opostas para aproveitar o espaço livre no meio. Se um invade o outro: stack overflow (o erro famoso) ou out of memory.

Erro comum: "se o programa não está rodando, ele não tem memória alocada". Verdade — programa no disco ocupa só espaço em disco, não em RAM. A alocação de memória RAM acontece quando o processo é criado, não quando o programa é instalado.
→ Próximo passo (seção 3): agora que você entende que processo = execução com estado, vamos ver onde o SO armazena esse estado. Toda essa informação (PC, registradores, memória, arquivos) precisa ficar em algum lugar — esse lugar tem nome.

3 PCB — onde mora o estado do processo

O sistema operacional precisa armazenar tudo o que vimos na seção 1 (PC, registradores, memória, arquivos abertos, estado) em algum lugar. Esse "lugar" é uma estrutura de dados chamada Process Control Block — abreviado PCB.

É só isso: um registro/struct que o kernel mantém para cada processo. Quando o SO precisa pausar o processo P1 e rodar P2, ele:

  1. Lê os registradores atuais da CPU e grava no PCB de P1
  2. Pega os valores do PCB de P2 e carrega nos registradores
  3. P2 retoma exatamente de onde tinha parado

Sem o PCB, essa troca seria impossível. Toda a "memória" que o SO tem sobre cada processo está no PCB.

Conteúdo do PCB

O PCB tem campos padronizados que aparecem em qualquer SO moderno (Linux, Windows, macOS):

Note que o PCB referencia (mas não contém) as tabelas de páginas e a memória do processo — essas são estruturas separadas. O PCB tem ponteiros para elas.

Onde fica o PCB?

O PCB fica em memória do kernel — área protegida, inacessível ao processo de usuário. Você não consegue, do seu programa, ler ou modificar o próprio PCB diretamente. Toda manipulação é feita por chamadas de sistema (syscalls).

Por que protegido? Se um processo pudesse modificar seu próprio PCB livremente, ele poderia, por exemplo, mudar sua prioridade para máxima e travar a CPU para si. A separação kernel/usuário é a primeira camada de segurança do SO.

O kernel mantém uma tabela de processos — basicamente um array (ou lista) de PCBs. Quando você roda ps ou Task Manager, está percorrendo essa tabela.

Exemplo real: Linux

No kernel do Linux, o PCB é a struct task_struct em include/linux/sched.h. Tem mais de 100 campos. Os principais:

Erro comum em prova: "código fonte do programa faz parte do PCB". Não — código fica em uma região da memória do processo (Text/Code, vista na seção 2). O PCB tem só metadados sobre o processo, não o código em si.
→ Próximo passo (seção 4): um dos campos do PCB é "estado atual". Mas que estados existem? Por que um processo às vezes está "rodando", às vezes "esperando"? Vamos ao diagrama de transição.

4 Estados de um processo

Um processo passa por vários "estados" ao longo de sua vida. Em cada momento, ele está em exatamente um estado. As transições entre estados acontecem por eventos: o SO escalonando, o processo pedindo I/O, etc.

O modelo mais ensinado e cobrado em prova tem 5 estados:

Novo
Acabou de ser criado. O SO está alocando recursos (PCB, memória inicial). Ainda não está pronto para rodar.
processo recém-criado por fork(), antes de ser admitido na fila de prontos
Pronto
Pode rodar, mas a CPU está ocupada com outro. Está na fila esperando o escalonador escolher.
tem tudo o que precisa para rodar — só falta a CPU ficar disponível
Executando
Está com a CPU agora. Em qualquer instante, no máximo um processo por núcleo está aqui.
CPU executando suas instruções; PC e registradores são "dele"
Bloqueado
Esperando algo que ainda não aconteceu. Pediu I/O, está esperando dados; ou esperando um lock; ou em sleep().
processo chamou read() do disco — fica bloqueado até o dado chegar
Terminado
Acabou. Já executou exit() ou foi morto. PCB ainda existe brevemente para o pai poder recuperar o status (zombie).
processo terminou normalmente (exit 0) ou abortou (sigsegv)

Quem causa cada transição?

Um detalhe importante: nem todas as transições são iguais. Algumas são causadas pelo SO, outras pelo próprio processo, outras por hardware externo. Entender isso ajuda a responder questões de prova:

TransiçãoQuem causaExemplo
Novo → ProntoSO (escalonador de longo prazo)fork() concluído, PCB pronto
Pronto → ExecutandoSO (escalonador de curto prazo)"chegou tua vez" (dispatch)
Executando → ProntoSO (timer / processo de prioridade maior)quantum expirou — preempção
Executando → BloqueadoPróprio processochamou read() — espera I/O
Bloqueado → ProntoHardware / outro processodisco respondeu, lock liberado
Executando → TerminadoPróprio processo ou SOexit() voluntário; ou kill -9

Observação chave: só o estado Executando pode ir para Bloqueado. Um processo no estado Pronto não pode pedir I/O — ele nem está rodando, então não tem como "chamar read()". Esse detalhe cai em prova (transições impossíveis).

Caso-limite: transições impossíveis

Algumas transições não existem nesse modelo. Saber por quê reforça o entendimento:

  • Pronto → Bloqueado: impossível. Para se bloquear, o processo precisa executar a chamada de sistema que pede I/O. Pronto não está executando.
  • Bloqueado → Executando: impossível. Quando o evento esperado acontece, o processo vai para Pronto primeiro. Para chegar a Executando ele precisa esperar o escalonador escolher.
  • Novo → Executando: impossível pelo mesmo motivo. Tem que passar por Pronto.

Regra geral: para ir parar em Executando, é obrigatório passar por Pronto (e ser escolhido pelo escalonador).

Variação que cai em prova: alguns livros incluem dois estados extras — Suspenso-Pronto e Suspenso-Bloqueado (quando o processo é movido da RAM para o swap em disco). Isso aparece quando se discute memória virtual em F5.3. O modelo de 5 estados é o "default"; o de 7 estados é uma extensão.
→ Próximo passo (seção 5): agora você sabe os estados. Mas como o estado "Novo" surge em primeiro lugar? Quem cria os processos? Vamos ver as syscalls fundamentais — fork, exec, wait, exit.

5 Criação e terminação de processos

Você acabou de ver que o estado "Novo" existe — mas como um processo chega a esse estado? Em sistemas Unix-like (Linux, macOS, BSD), todo processo é criado por outro processo, formando uma árvore de processos. A raiz é o processo init (ou systemd) com PID 1, criado pelo kernel na inicialização.

O Unix tem 4 chamadas de sistema fundamentais para gerenciar processos:

fork()
Cria um processo filho copiando o pai. Retorna 2 vezes: 0 no filho, PID do filho no pai. É o único jeito de criar processos no Unix.
if (fork() == 0) { /* filho */ } else { /* pai */ }
exec()
Substitui o programa atual por outro. Não cria processo novo — reaproveita o PCB e troca a memória/código. Família: execv, execvp, execve...
execvp("ls", ["ls", "-l", NULL]) — esse processo agora "é" o ls
wait()
Pai espera filho terminar. Bloqueia até algum filho fazer exit. Retorna o PID do filho que terminou + status.
int status; pid_t pid = wait(&status); — bloqueia aqui até ter filho morto
exit(code)
Termina o processo atual. Libera quase tudo, mantém o PCB com status até o pai chamar wait. code é o "valor de retorno" para o shell.
exit(0) — sucesso. exit(1) — erro genérico. echo $? mostra o último.

O padrão fork-exec — como o shell roda comandos

Quando você digita ls no terminal, o que acontece? O shell não vira o ls — ele cria um filho que vira o ls. Esse padrão é onipresente:

1// shell vê comando "ls -l" digitado pelo usuárioinício
Shell tem PID = 4000 (digamos). Ele leu a linha de comando e identificou que precisa rodar o programa ls com argumento -l.
2pid_t pid = fork(); fork
Aqui é o ponto mágico. fork() faz uma cópia EXATA do shell. Agora existem 2 processos: pai (PID 4000) e filho (PID 4001, digamos). Os dois retornam de fork() — mas com valores diferentes. No pai, pid = 4001. No filho, pid = 0. Mesmo código, dois fluxos.
3if (pid == 0) { filho
Esse if só é verdadeiro no filho, porque fork() retornou 0 lá. No pai, pid = 4001 (não-zero), então o else é executado.
4 execvp("ls", argv); exec
O filho substitui sua memória pelo programa ls. O PID continua 4001 (mesmo PCB), mas o código, dados, heap, stack são todos trocados. A partir daqui, o processo 4001 "é" o ls, não mais uma cópia do shell. Se exec() bem-sucedido, esta linha não retorna.
5 perror("exec failed"); erro
Esta linha só executa se exec() falhar (programa não existe, sem permissão). Caso contrário, o controle nunca volta para cá.
6 exit(1);erro
Termina o filho com código de erro 1.
7} else { pai
Branch do pai (shell). pid = 4001 — sabe quem é o filho.
8 int status;var
Variável para receber o status de saída do filho.
9 waitpid(pid, &status, 0); wait
Pai bloqueia (estado Bloqueado!) até o filho terminar. Quando o ls terminar, o kernel desbloqueia o shell e coloca o status em status. É por isso que o terminal "espera" o ls antes de mostrar o prompt de novo.
10 printf("ls terminou: %d\n", status);final
Shell mostra o prompt novamente. Loop volta para ler o próximo comando.

Por que separar fork de exec?

Pode parecer estranho criar um clone só para imediatamente substituí-lo por outro programa. Por que não uma chamada única "criar+executar"? Razões:

  • Flexibilidade: entre fork e exec, o filho pode configurar coisas: redirecionar stdout para um arquivo, fechar arquivos, mudar diretório, definir variáveis de ambiente. É assim que ls > output.txt funciona.
  • Pipes: a famosa pipe cat file | grep foo requer fork-exec separados — entre eles, o shell conecta os file descriptors dos dois filhos.
  • Segurança: filho pode largar privilégios (passar de root para usuário comum) antes de executar o programa. Isso é como servidores web rodam scripts CGI com segurança.

Estados especiais: zumbi e órfão

Dois conceitos que aparecem em prova:

EstadoQuando ocorreProblema?
Zumbi Filho terminou, mas pai ainda não chamou wait(). PCB persiste para que o pai possa ler o status. Sim — se acumular muitos zumbis, esgota a tabela de processos. Programadores devem sempre fazer wait() ou usar SIGCHLD.
Órfão Pai terminou antes do filho. Filho continua rodando sem pai original. Não — kernel automaticamente "adota" o órfão para o init (PID 1), que faz wait() periodicamente. Sem vazamento.
Pegadinha clássica em prova: "Um processo pai termina antes do filho. O filho..." — alternativa errada típica é "também termina automaticamente". Não termina. Vira órfão e é adotado pelo init. Continua rodando até terminar sozinho.
→ Próximo passo (seção 6): fork copia tudo. PCB inteiro, memória, arquivos. Para um web server que precisa atender 10.000 conexões, isso é caro demais. Existe um caminho mais leve — threads.

6 Threads — execução leve dentro do processo

Imagine um web server que atende 10.000 conexões simultâneas. Se cada conexão é um processo (criado por fork), o SO precisa manter 10.000 PCBs, 10.000 espaços de memória completos, 10.000 tabelas de páginas. O custo é proibitivo: criar um processo leva milissegundos, e cada um ocupa megabytes de memória.

A solução: threads. Uma thread é um fluxo de execução dentro de um processo. Múltiplas threads dentro do mesmo processo compartilham memória. Você pode ter milhares de threads em um único processo, com custo muito menor.

🏠 Processo

Casa inteira

Todos os móveis (memória), endereço próprio (espaço de endereçamento). Se você quer outra "casa", constrói uma cópia inteira (fork).

🛏️ Thread

Quarto na casa

Mesma casa, mesmos móveis (memória compartilhada). Cada quarto tem seu próprio ocupante, mas todos usam a mesma cozinha. Adicionar quarto é barato.

O que threads compartilham vs. não compartilham

Esse é o ponto que mais cai em prova. Decore o que está em qual coluna:

✅ Compartilhado entre threads do mesmo processo
  • Code (Text) — instruções do programa
  • Data — variáveis globais e estáticas
  • Heap — memória alocada com malloc/new
  • Arquivos abertos — file descriptors
  • Espaço de endereçamento virtual
  • Handlers de sinais — o que fazer ao receber cada sinal
❌ Privado a cada thread
  • Stack — pilha de chamadas (variáveis locais)
  • Registradores da CPU
  • Program Counter (PC)
  • Thread ID (TID)
  • Signal mask — quais sinais cada thread bloqueia
  • Estado de escalonamento

Regra prática: threads compartilham tudo o que pertence ao "ambiente do programa" (código, dados, recursos), mas têm execução independente (cada uma com seu PC e pilha).

Visualização: memória de processo único com 2 threads

PROCESSO P (1 espaço de endereçamento)

Note como cada thread tem sua própria stack (laranja vs azul-claro), mas o resto da memória (verde) é compartilhado. Variável global declarada no código pode ser lida e escrita por qualquer thread — e é exatamente isso que abre a porta para race conditions (assunto de F5.2).

Modelos de implementação de threads

Como o SO percebe e gerencia threads? Há três modelos clássicos. Eles se diferenciam pela razão entre threads de usuário e threads de kernel:

M:1
user-level threads

Várias threads de usuário mapeadas em uma thread do kernel. SO só vê o processo.

VantagensCriação extremamente rápida (sem syscall). Switch barato. Funciona em qualquer SO.
DesvantagensSe uma thread bloqueia (I/O), todas bloqueiam. Sem paralelismo real em multi-core.
1:1
kernel-level threads

Cada thread de usuário corresponde a uma thread do kernel. SO vê e escalona cada thread individualmente.

VantagensParalelismo real em multi-core. Bloqueio em uma thread não afeta as outras.
DesvantagensCriação envolve syscall (mais cara). Cada thread consome recursos do kernel.
M:N
híbrido

M threads de usuário multiplexadas sobre N threads de kernel (M ≥ N). Combina os dois.

VantagensCompromisso: paralelismo real + criação rápida. Boa escalabilidade.
DesvantagensImplementação complexa. Difícil afinar. Quase abandonado na prática moderna.

Hoje em dia (Linux, Windows, macOS modernos): usam o modelo 1:1. Linux Threads, NPTL, Windows Threads — cada thread de usuário tem sua thread de kernel correspondente.

Qual o ganho prático?

OperaçãoProcesso (fork)Thread (pthread_create)
Tempo típico de criação~1 ms~10–100 µs
Memória inicial~MB (cópia da memória do pai)~KB (só nova stack)
Comunicação internaIPC (pipe, msgqueue, shm) — caroMemória compartilhada direta — grátis
IsolamentoTotal — crash não afeta outrosNenhum — crash em uma derruba o processo

Esse último ponto é importante: threads são mais rápidas e leves, mas menos seguras. Um segfault em uma thread mata o processo inteiro (e todas as outras threads junto). Por isso navegadores modernos como o Chrome usam processos separados para cada aba, mesmo que mais caros — se uma aba travar, as outras continuam.

Erro comum: "thread = processo leve, fundamentalmente igual". Não. Threads compartilham memória — uma altera variável global e a outra vê na hora. Processos não. Essa diferença muda completamente o modelo de programação (sincronização vira fundamental para threads, irrelevante para processos isolados).
→ Próximo passo (seção 7): processos não compartilham memória. Mas frequentemente precisam trocar dados (shell envia comando para o filho; pipes entre comandos). Como isso funciona? IPC.

7 IPC — Comunicação entre processos

Processos têm espaços de endereçamento isolados — esse é seu recurso de segurança mais importante. Mas frequentemente precisam trocar informações: o shell precisa receber stdout do ls; o navegador precisa enviar URLs para o processo de rede; o seu programa precisa logar em um arquivo lido por outro processo.

IPC (Inter-Process Communication) é o conjunto de mecanismos que o SO oferece para essa comunicação controlada entre processos isolados.

Mecanismos de IPC

Existem 4 famílias principais. Cada uma tem trade-offs e cenários de uso:

MecanismoModeloVelocidadeUsar quando...
Pipe fluxo unidirecional média Pai e filho relacionados precisam de comunicação simples (stdin/stdout encadeado)
Named Pipe (FIFO) fluxo unidirecional média Processos não-relacionados precisam se comunicar — mas no mesmo computador
Fila de mensagens mensagens discretas média Múltiplos remetentes/destinatários, mensagens com tipos/prioridades
Memória compartilhada região de memória comum altíssima Volume grande de dados, baixa latência crítica (acesso direto à memória)
Sockets fluxo ou datagrama variável Comunicação em rede; ou processos locais via Unix sockets
Sinais notificação assíncrona rápido (sem dado) Avisar evento (Ctrl+C → SIGINT, processo morrer → SIGCHLD); não para transferir dados

Pipe — o mecanismo do shell

Quando você escreve cat arquivo.txt | grep erro, o shell:

  1. Cria um pipe (canal unidirecional com duas pontas: leitura e escrita)
  2. fork → cria cat, redireciona stdout para a ponta de escrita
  3. fork → cria grep, redireciona stdin para a ponta de leitura
  4. cat escreve no pipe → grep lê do pipe → fluxo encadeado

É o IPC mais antigo do Unix. Ainda muito usado por ser simples e eficiente.

Memória compartilhada — o mais rápido

Os outros mecanismos passam pelo kernel: o processo A chama write(), kernel copia os dados para um buffer, processo B chama read(), kernel copia do buffer para B. Duas cópias, duas syscalls.

Memória compartilhada elimina isso: kernel mapeia a mesma página de memória física em ambos os processos. A escreve diretamente, B lê diretamente. Sem cópia, sem syscall na operação. Velocidade comparável a acesso à memória normal.

O preço: velocidade vem com responsabilidade. Sem coordenação, A e B podem escrever simultaneamente, lendo lixo um do outro. Race conditions precisam ser gerenciadas com semáforos, mutexes etc — assunto principal do F5.2 Sincronização.

Modelo de troca de mensagens vs. memória compartilhada

Em um nível mais abstrato, todos os mecanismos de IPC se reduzem a duas filosofias:

📨 Troca de mensagens
  • Processos enviam/recebem mensagens
  • Kernel media a comunicação
  • Funciona local e em rede
  • Sincronização implícita (recv bloqueia)
  • Mais lento, mais seguro
  • Ex: pipes, filas, sockets
🧠 Memória compartilhada
  • Processos veem mesma região de memória
  • Kernel só configura no início; depois sai do caminho
  • Só funciona local (mesma máquina)
  • Sincronização explícita obrigatória
  • Mais rápido, mais perigoso
  • Ex: shm, mmap, threads (de graça)

Sinais — uma família à parte

Sinais não são para transmitir dados — são para notificar eventos. Cada sinal é um número/nome. Lista famosa:

SinalCausaDefault
SIGINTCtrl+C no terminalTermina o processo
SIGTERMkill PID — pedido educado para terminarTermina o processo (programa pode capturar para limpar)
SIGKILLkill -9 PID — não pode ser ignoradoTermina imediatamente, sem cleanup
SIGSEGVAcesso a memória inválidaTermina + core dump
SIGCHLDFilho terminouIgnorado (mas notifica o pai)

O programador pode capturar quase qualquer sinal e definir o que fazer (SIGKILL e SIGSTOP são as únicas exceções absolutas — kernel sempre obedece). Isso permite servidores fazerem cleanup gracioso ao receber SIGTERM, por exemplo.

8 Context Switch — o custo de alternar

Você viu na motivação que o SO alterna entre processos para criar a ilusão de simultaneidade. Esse "alternar" tem nome técnico: context switch. É o conjunto de operações que o kernel faz para tirar um processo da CPU e colocar outro.

O que acontece em um context switch

Suponha que P1 está rodando e o escalonador decide trocar para P2. Os passos:

1
Interrupção entra (timer, syscall, I/O completed). CPU para o que está fazendo e salta para o handler do kernel.
2
Kernel salva o contexto de P1: grava todos os registradores da CPU (PC, SP, R0..R15, flags) no PCB de P1.
3
Kernel decide quem rodar a seguir (escalonador — assunto de F5.2). Suponha que escolheu P2.
4
Kernel troca contexto de memória: aponta a MMU para a tabela de páginas de P2. Isso pode invalidar a TLB (cache de tradução de endereços).
5
Kernel restaura o contexto de P2: lê os registradores do PCB de P2, carrega na CPU.
6
CPU retoma execução de P2 a partir do PC restaurado. P2 continua exatamente de onde tinha parado.

Por que custa caro?

Um context switch demora tipicamente entre 1 e 10 microssegundos. Pode parecer pouco, mas se o SO faz mil switches por segundo, são até 10 milissegundos só de overhead — 1% da CPU "perdido" em troca de contexto.

Os custos vêm de:

ComponenteCusto diretoCusto indireto (cache)
Salvar/restaurar registradores~30 cycles—
Trocar tabela de páginas (MMU)~100 cyclesTLB invalidada → faltas de página subsequentes (centenas de cycles cada)
Mudança kernel ↔ user mode~100 cycles—
Cache da CPU (L1, L2)—P2 acessa dados que não estão em cache → cache miss explosivo nos primeiros milhares de instruções

O custo indireto (cache, TLB) é normalmente maior que o direto. Pode levar centenas de microssegundos para o cache "esquentar" de novo.

Thread context switch é mais barato

Se o SO troca entre duas threads do mesmo processo:

  • Salva e restaura registradores: sim (igual a process switch)
  • Troca tabela de páginas: não (mesmo processo, mesma tabela)
  • TLB e cache: preservados (mesmo espaço de endereçamento)

Resultado: thread switch é tipicamente 2 a 10 vezes mais rápido que process switch. Um dos motivos pelos quais threads são preferidas em servidores de alta performance.

Trade-off: quão rápido alternar?

Se o SO alterna processos a cada 1 ms (quantum curto): processos têm resposta rápida (bom para interatividade), mas overhead de switch é grande.

Se o SO alterna a cada 100 ms (quantum longo): pouco overhead, alta vazão (throughput) total. Mas processos ficam "presos" esperando quando outro está rodando — péssimo para sistemas interativos.

Diferentes SOs e diferentes contextos escolhem trade-offs diferentes. Sistemas de tempo real usam quanta extremamente curtos. Sistemas batch usam quanta longos. Sistemas desktop ficam no meio (5–20 ms é típico no Linux).

Erro comum: "context switch ocorre só quando o quantum termina". Falso. Ocorre em qualquer momento que o SO precise tirar o processo: quantum expirou, processo bloqueou (chamou read), processo de prioridade maior ficou pronto, processo voluntariamente cedeu (yield), etc.

Como contar context switches no Linux

Comando: cat /proc/PID/status | grep ctxt. Mostra quantos voluntários (processo bloqueou em I/O) e involuntários (preempção).

Em sistemas com muitos context switches involuntários: sinal de "thrashing" — escalonador está alternando demais, normalmente porque há mais processos prontos que núcleos disponíveis e quanta muito curtos.

Conexão com escalonamento (próximo módulo): a política que decide quando trocar processos e qual escolher se chama escalonamento. F5.2 cobre os algoritmos clássicos: FCFS, SJF, Round Robin, Priority, MLFQ. Cada um faz trade-offs diferentes entre throughput, fairness e response time.

10 Resumo

🎯 O que você precisa dominar deste módulo

Programa é arquivo estático no disco; processo é a execução em andamento, com PID, estado e memória próprios
PCB (Process Control Block) guarda PID, estado, PC, registradores, memória, arquivos abertos — tudo necessário para pausar/retomar
Memória do processo dividida em Text, Data, Heap, Stack. Stack e Heap crescem em direções opostas
5 estados clássicos: Novo → Pronto ↔ Executando → Terminado, com Bloqueado para esperar I/O
Para chegar a Executando, é obrigatório passar por Pronto (escalonador escolhe)
fork() cria filho copiando pai; exec() substitui programa do processo atual; wait() faz pai esperar filho; exit() termina
Padrão fork-exec é como o shell roda comandos. Zumbi: filho terminou mas pai não fez wait. Órfão: pai terminou primeiro — adotado pelo init
Threads compartilham Code/Data/Heap/arquivos do processo, mas têm Stack/registradores/PC próprios
Modelos: M:1 (user-level, rápido mas serial), 1:1 (kernel-level, padrão moderno), M:N (híbrido, complexo)
IPC: pipe (pai-filho), FIFO (não relacionados), memória compartilhada (mais rápido), sockets (rede), sinais (notificação sem dado)
Context switch custa ~1–10 µs. Trocar entre threads do mesmo processo é mais barato que entre processos (sem trocar tabela de páginas/TLB)
