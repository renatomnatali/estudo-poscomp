Como medir a eficiência de algoritmos independente do hardware — a linguagem universal da ciência da computação

1 Por que medir a eficiência?

Imagine dois algoritmos que resolvem o mesmo problema. Como saber qual é melhor? Cronometrar em um computador específico é inútil: o resultado muda com o hardware, a linguagem de programação e os dados de entrada. Precisamos de uma medida independente de máquina.

Abordagem errada ✗

Cronometrar a execução

Depende do CPU, RAM, compilador, carga do sistema. Não generaliza.

Abordagem certa ✓

Contar operações em função de n

Expressa o comportamento para qualquer tamanho de entrada n.

Insight central: nos interessa o comportamento quando n cresce — não o tempo exato para n = 100, mas o que acontece quando n vai para 1.000, 1.000.000, ∞.

O que é esse "n"?

n representa o tamanho da entrada do seu algoritmo — a "quantidade de dados" que ele precisa processar. O que exatamente é n depende do problema:

📋
Ordenar uma lista
n = quantidade de itens
ex: ordenar 50 nomes vs 50.000 nomes
🔍
Buscar em um arquivo
n = número de linhas
ex: buscar em 200 registros vs 2.000.000
🔗
Caminho em um grafo
n = número de nós (ou arestas)
ex: rotear em 10 cidades vs 10.000
Regra prática: sempre que você ver "n" numa notação de complexidade, pergunte: "n é quantos quês?" — e a resposta define o que o algoritmo está processando.
→ Próximo passo (seção 2): agora que você sabe o que é n, vamos entender as três formas de descrever como um algoritmo se comporta à medida que n cresce.

2 As três notações

Antes de ver as definições formais (seção 3), você precisa entender para que serve cada notação. Pense assim: você quer descrever o quão rápido seu algoritmo cresce. Mas "rápido" tem três sabores distintos.

🌧️ Analogia: previsão do tempo

Um meteorologista pode dizer: "vai chover no máximo 50mm" (limite superior), "vai chover pelo menos 10mm" (limite inferior), ou "vai chover entre 20mm e 30mm" (intervalo exato). São três formas de descrever a mesma chuva — com precisões diferentes.

⏱️ Na análise de algoritmos

Você pode dizer: "nunca piora além de n²" (Big-O), "nunca melhora além de n" (Ômega), ou "sempre fica entre n e n²" (Theta). São três formas de descrever o mesmo custo.

O
Big-O — "no máximo"
Lê-se: "Ó grande de n" — lê-se sempre com a expressão dentro: O(n²) é "Ó grande de n ao quadrado", O(log n) é "Ó grande de log n".

Significa: o algoritmo nunca é mais lento que isso. É o teto.

Exemplo: busca linear em lista de n itens.
No pior caso você percorre tudo: O(n).
Se o item for o primeiro, termina em 1 passo — mas dizemos O(n) porque no pior caso é isso.

É a notação mais usada em entrevistas e POSCOMP
Ω
Ômega — "no mínimo"
Lê-se: sempre com a expressão dentro: Ω(n) é "Ômega de n", Ω(n log n) é "Ômega de n log n".

Significa: o algoritmo nunca é mais rápido que isso. É o piso.

Exemplo: para ordenar n itens, você precisa no mínimo ler cada item uma vez: Ω(n). Não existe algoritmo de ordenação baseado em comparação mais rápido que Ω(n log n).

Importante para provar que nenhum algoritmo pode fazer melhor
Θ
Theta — "exatamente"
Lê-se: "Teta de n log n"

Significa: teto e piso são a mesma função. O custo fica preso entre dois múltiplos de g(n).

Exemplo: Merge Sort é Θ(n log n) — melhor e pior caso crescem da mesma forma.

É a descrição mais precisa, mas nem sempre existe (ex: busca linear não tem Theta único)

Como as três se relacionam

Pense em Theta como a interseção de O e Ω:

f(n) = O(n²) → f(n) pode crescer até n². Também vale O(n³), O(2ⁿ)…
f(n) = Ω(n) → f(n) cresce pelo menos como n. Também vale Ω(log n), Ω(1)…
f(n) = Θ(n log n) → f(n) fica preso entre c₁·n log n e c₂·n log n. Implica O(n log n) e Ω(n log n).
Atenção — erro comum: "O(n²) significa que o algoritmo sempre faz n² operações." Errado. O significa no máximo. Um algoritmo O(n²) pode terminar em n operações para certas entradas — o que não pode é ultrapassar n² operações no pior caso.
→ Próximo passo (seção 3): você já sabe o que cada notação significa. Agora vamos ver a definição matemática precisa — e descobrir que ela é mais simples do que parece quando você sabe o que cada símbolo representa.

3 Definição formal — entendendo cada peça

Antes de qualquer fórmula, vamos traduzir cada símbolo para português. A confusão geralmente não é com a matemática em si — é porque ninguém explica o que cada letra significa.

n
O tamanho da entrada. É o único número que varia. Tudo mais na análise é em função de n.
n = 10 → lista com 10 itens  |  n = 10.000 → lista com 10 mil itens
f(n)
O custo real do seu algoritmo. Pode ser uma expressão feia, como 3n² + 5n − 2.
f(n) = 3n² + 5n → para n=10: custa 3(100)+5(10) = 350 operações
g(n)
A função de referência — mais simples. Você escolhe uma função "limpa" (n², n, log n…) para servir de régua de comparação. Não é o custo real — é o "molde".
g(n) = n² → "quero comparar meu algoritmo com n²"
c
Uma constante que absorve coeficientes. Você escolhe o valor — só precisa existir algum c positivo que faça a desigualdade funcionar.
c = 8 → mostra que 3n² + 5n ≤ 8·n² para todo n ≥ 1
Por que c não é inútil? Sem ele, a definição exigiria f(n) ≤ g(n) — e aí 5n² = O(n²) seria falso, porque 5n² nunca é ≤ n². O c é o "curinga" que diz: "pode multiplicar g(n) pelo que precisar". Isso torna constantes multiplicativas irrelevantes na notação final — um computador 5× mais lento é só c = 5, e ainda é O(n²).
n₀
O ponto de corte — "a partir daqui vale para sempre". Para n pequeno, a relação pode não valer. Mas a partir de n₀, vale para todo n maior.
n₀ = 1 → a partir de n=1, 3n²+5n ≤ 8n² vale eternamente
O que é "n grande"? É só uma forma de dizer "quando n já passou do n₀". Antes disso, constantes e termos menores ainda fazem barulho — por exemplo, f(n) = 1000n + 5 pode ser maior que n² para n pequeno. Mas a partir de um certo ponto (n₀ ≈ 1001), n² passa 1000n e nunca mais perde. "N grande" é esse regime onde a classe de crescimento já revelou sua natureza real.
O(g)
Como se lê: "Ó grande de g de n" ou "na ordem de g de n".
O que significa: "meu algoritmo não cresce mais rápido que g(n), a partir de algum ponto".
O(n²) → "não cresce mais rápido que n²" — se n dobra, o custo no máximo quadruplica

A intuição em uma frase

f(n) = O(g(n)) significa: existe uma versão "inflada" de g(n) — ou seja, c·g(n) — que fica sempre acima de f(n) depois de um certo ponto n₀. Não importa quanto n cresça, f(n) nunca ultrapassa esse teto.

Veja no gráfico — f(n) = 3n² + 5n vs. g(n) = n²

Animação: por que 3n² + 5n = O(n²)?

f(n) = 3n² + 5n (seu algoritmo)
c·g(n) = 8n² (teto — limite superior)
n₀ = ponto a partir do qual o teto nunca é ultrapassado
Observe: f(n) azul fica sempre abaixo do teto laranja após n₀

Agora a fórmula — cada parte já faz sentido

Big-O — limite superior
f(n) = O(g(n))  ⟺  ∃ c > 0, n₀  :  f(n) ≤ c·g(n)   ∀ n > n₀
⟺ = "se e somente se" (as duas frases dizem a mesma coisa)
∃ = "existe" (basta um funcionar)
c > 0 = constante livre que você escolhe
n₀ = ponto de corte
≤ = f(n) não ultrapassa o teto c·g(n)
∀ n > n₀ = "para todo n maior que n₀"

Prova passo a passo: 3n² + 5n = O(n²)

Agora que você sabe o que cada símbolo significa, a prova é só "achar um c e um n₀ que funcionem":

1
O que precisamos provar: que existe algum c onde 3n² + 5n ≤ c·n² para n grande o suficiente. Não sabemos c ainda — vamos calcular.
2
Substituição: para n ≥ 1, sabemos que n ≤ n² (qualquer número inteiro positivo é menor ou igual ao seu quadrado). Logo 5n ≤ 5n².

Com isso, substituímos o termo 5n por algo maior (5n²) na expressão original:

Passo A (desigualdade): 3n² + 5n  ≤  3n² + 5n²
Trocamos 5n por 5n², que é maior — então o lado direito só cresce. A desigualdade vale.

Passo B (igualdade): 3n² + 5n²  =  8n²
Álgebra simples: (3+5)n² = 8n². Igual a 3x + 5x = 8x.

Juntando os dois passos: se A ≤ B e B = C, então A ≤ C.
Conclusão: 3n² + 5n  ≤  8n²
3
Identificamos c e n₀. A prova do Passo 2 usou a condição "para n ≥ 1". Esse "n ≥ 1" é exatamente o n₀ — ele não foi escolhido no ar, emergiu da condição que a própria substituição precisava. E o teto que encontramos foi 8n², então c = 8.

Valores: c = 8 e n₀ = 1. Para todo n ≥ 1: 3n² + 5n ≤ 8n² ✓

Teste: n=10 → 3(100)+5(10)=350 ≤ 8(100)=800 ✓   n=100 → 30.500 ≤ 80.000 ✓
4
Conclusão: 3n² + 5n = O(n²).

Note: c ≥ 8 e n ≥ 1. Não é qualquer c > 0 — c = 1 não funcionaria, pois 3n² + 5n ≤ 1·n² é falso. O c precisa ser grande o suficiente para o teto cobrir f(n). Qualquer c ≥ 8 funciona porque o teto fica mais folgado ainda — o que a definição exige é apenas que exista pelo menos um.
5
Por que não O(n)? Tente: seria 3n² + 5n ≤ c·n. Para n grande, 3n²/n = 3n → cresce sem limite. Nenhum c fixo consegue cobrir isso. Logo O(n) não vale.

5 Regras práticas para calcular Big-O

Antes de listar as regras, veja o seguinte código. Você consegue estimar qual bloco domina o tempo total?

1for i in range(n): O(n)
2 print(i)
3for i in range(n): O(n²)
4 for j in range(n):
5 print(i, j)

Para n = 1.000: o bloco 1 faz 1.000 operações. O bloco 2 faz 1.000.000. A soma é 1.001.000 — que na prática é indistinguível de 1.000.000. O bloco menor desaparece.

Esse exemplo já mostra as três ideias centrais das regras a seguir: loops sequenciais somam, loops aninhados multiplicam, e o termo maior engole os menores. As regras são só formas precisas de aplicar esses três fatos.

Regra 1 — Eliminar constantes multiplicativas

Pense em loops idênticos executados um após o outro:

for i in range(n): print(i)   ← O(n)
for i in range(n): print(i)   ← O(n)
for i in range(n): print(i)   ← O(n)
for i in range(n): print(i)   ← O(n)
for i in range(n): print(i)   ← O(n)
# Total: 5n operações — mas o pior caso ainda cresce como n
# → O(n), não O(5n)

Se n dobra, os cinco loops juntos ainda dobram. Se n quadruplica, os cinco juntos ainda quadruplicam. O formato do crescimento é n — não importa se são 5 loops ou 500.

O mesmo vale para qualquer expressão com coeficiente: 5n², 1000n, 0.001·2ⁿ. O coeficiente não muda a classe de crescimento.

Por quê formalmente? Pela definição de Big-O, você escolhe qualquer c. Para 5n² = O(n²), escolhe c = 5 e n₀ = 1:
5n² ≤ 5·n²  para todo n ≥ 1  ✓
O coeficiente 5 vira o parâmetro c — e c some da notação final.

Regra 2 — O termo maior engole os menores

Você acabou de ver isso: o bloco O(n) desapareceu diante do O(n²). A mesma coisa acontece dentro de uma expressão com vários termos. Para n = 1.000, veja o quanto cada termo contribui para n³ + n² + n + 1:

n³ representa 99,9% do total. Os outros termos existem, mas são irrelevantes para n grande. Por isso n³ + n² + n + 1 = O(n³) — o enunciado formal do que você acabou de observar na tabela.

Prova formal: n² ≤ n³ para n ≥ 1, então n³ + n² ≤ n³ + n³ = 2n³. Com mais dois termos, c = 4 cobre tudo: n³ + n² + n + 1 ≤ 4n³. ✓

Regra 3 — Loops aninhados se multiplicam

O loop interno executa completamente para cada iteração do externo. É multiplicação, não soma.

for i in range(n):         ← executa n vezes
    for j in range(n):     ← executa n vezes POR iteração do externo
        print(i, j)        ← total: n × n = n² execuções

Pense assim: loop externo percorre linhas, loop interno percorre colunas. Você percorre uma matriz inteira: n × n = n².

Regra 4 — Loops sequenciais se somam (e o maior domina)

for i in range(n):         ← O(n)
    print(i)

for i in range(n):         ← O(n²) (loop aninhado)
    for j in range(n):
        print(i,j)

# Total: O(n) + O(n²)
# Como n² domina n para n grande: O(n²)

Para n = 1.000: bloco 1 faz 1.000 ops; bloco 2 faz 1.000.000 ops. A soma é 1.001.000 ≈ 1.000.000 = n². O menor é irrelevante.

E quando o código chama a si mesmo? As quatro regras acima funcionam para código iterativo — loops. Quando uma função chama a si mesma (recursão), o custo não pode ser calculado diretamente: ele precisa ser descrito como uma equação que se refere a si mesma. Esse é o tema do próximo módulo.

6 Exemplos resolvidos

Exemplo A — Classificar a complexidade

Qual a complexidade de: f(n) = 7n³ + 4n² log n + 12n − 8?

1
Identificar todos os termos: 7n³, 4n² log n, 12n, 8
2
Comparar crescimento: n³ > n² log n > n > 1. O termo dominante é 7n³.
3
Eliminar constante multiplicativa: 7n³ → n³
4
Resposta: f(n) = O(n³) e também Θ(n³)

Exemplo B — Análise de código (clique nas linhas para ver a explicação)

1def exemplo(arr):O(1)
Definição da função — acontece uma vez só. Custo: O(1).
2 n = len(arr)O(1)
len() retorna o tamanho em tempo constante. Custo: O(1).
3 total = 0O(1)
Atribuição simples. Custo: O(1). Não importa o valor de n.
4 for i in range(n): O(n)
Loop que repete exatamente n vezes. O corpo (linha 5) custa O(1) cada iteração. Total do bloco: n × O(1) = O(n).
5 total += arr[i] O(1)
Soma e acesso a array por índice. Custo: O(1) por execução. Mas executa n vezes (veja linha 4).
6 for i in range(n): O(n²)
Loop externo: n iterações. O loop interno (linha 7) também roda ~n vezes. Resultado: n × n = O(n²). Este bloco domina tudo.
7 for j in range(i): O(n)
Loop interno: roda i vezes. No pior caso i = n−1 ≈ n. Somando sobre todas as iterações do loop externo: 0+1+2+…+(n−1) = n(n−1)/2 ≈ n²/2 = O(n²).
8 print(arr[i], arr[j])O(1)
print() e dois acessos a array: O(1) por execução. Mas é chamado O(n²) vezes pelo par de loops aninhados.
9 return total O(1)
Retorno simples. Custo: O(1).
Análise final: O(1) + O(n) + O(n²) + O(1) = O(n²)
Loops sequenciais somam, mas o maior domina. O loop aninhado (linhas 6–8) engole todo o resto.

Exemplo C — Busca binária vale O(log n)?

Primeiro: o que é log₂(n) na prática? É a quantidade de vezes que você consegue dividir n por 2 até chegar em 1.
n = 16 → 16÷2=8 → 8÷2=4 → 4÷2=2 → 2÷2=1  → 4 divisões → log₂(16) = 4
n = 1024 → 10 divisões → log₂(1024) = 10
n = 1.000.000 → ~20 divisões → log₂(10⁶) ≈ 20

Intuição: logaritmo cresce muito devagar. Dobrar n adiciona apenas 1 passo.
1
O que a busca binária faz: a cada passo, compara o elemento do meio com o alvo. Se não achou, descarta metade do array e repete.
n → n/2 → n/4 → n/8 → … → 1
Exemplo: array de 16 itens → 8 → 4 → 2 → 1 → encontrou (ou não existe). Máximo 4 passos.
2
Quantos passos até sobrar 1 elemento?
Depois de k divisões, sobram n/2ᵏ elementos. Queremos n/2ᵏ = 1:
n = 2ᵏ  →  k = log₂(n)
Isso é só a definição de logaritmo: "k tal que 2ᵏ = n".
3
Cada passo custa O(1) (uma comparação). São log₂(n) passos.
Total: log₂(n) × O(1) = O(log n) ✓
Nota: log₂ e log₁₀ diferem só por uma constante (log₂n = log₁₀n / log₁₀2 ≈ 3.32·log₁₀n). Como constantes somem no Big-O, escrevemos apenas O(log n).
4
Por que isso importa? Compare com busca linear O(n):
O(n) — linear
n = 1.000.000 → até 1 milhão de passos
O(log n) — binária
n = 1.000.000 → até 20 passos
Isso explica por que banco de dados usam índices (busca binária) em vez de varrer a tabela inteira.

8 Resumo

🎯 O que você precisa dominar

O(f(n)) é o limite superior — "no máximo tão ruim quanto g(n)"
Ω(f(n)) é o limite inferior — "no mínimo tão bom quanto g(n)"
Θ(f(n)) é o limite exato — implica ambos O e Ω
Para calcular: elimine constantes e termos menores, fique com o dominante
Hierarquia: O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ)
Loops aninhados multiplicam complexidades; loops sequenciais somam (e o maior domina)
