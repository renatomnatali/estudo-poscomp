Como calcular o custo de algoritmos recursivos — dos três métodos ao Teorema Mestre
1. Por que recorrências? 2. Anatomia 3. Método 1: Expansão 4. Método 2: Árvore 5. Método 3: Teorema Mestre 6. Exemplos resolvidos 7. Quiz 8. Resumo

1 Por que recorrências?

Em F1.2 você aprendeu a calcular o custo de algoritmos iterativos — loops. A última regra deixou uma pergunta em aberto: e quando uma função chama a si mesma? As quatro regras de loops não conseguem responder. O custo não pode ser calculado diretamente porque ele depende do custo de chamadas menores, que dependem de chamadas ainda menores — e assim por diante.

Você já viu isso acontecer em F1.1: o Merge Sort divide o array ao meio, ordena cada metade, e junta. Para saber o custo total, você precisa saber o custo de ordenar a metade — que por sua vez depende do custo de ordenar um quarto, e assim sucessivamente. A análise de loops trava aqui.

Por que loops não bastam?

Para loops, você conta iterações: um loop de n vezes custa O(n). Mas em recursão, o número de "iterações" depende do tamanho do subproblema — e esse tamanho muda a cada chamada. A mesma função com n=8 chama a si mesma com n=4, que chama com n=2, que chama com n=1. Não dá para contar isso como um loop simples.

A ferramenta certa: equação de recorrência

A solução é descrever o custo em função de si mesmo: "o custo para n elementos é igual ao custo para n/2 elementos, mais o trabalho de juntar os resultados". Essa é uma equação de recorrência — e resolver ela nos dá o Big-O. É isso que este módulo ensina.

Três formas de resolver uma recorrência

Este módulo apresenta três métodos em ordem crescente de poder. Você vai entender cada um antes de ver o próximo:

1
Expansão
Abrir a equação passo a passo até enxergar o padrão.
2
Árvore de recorrência
Desenhar quem chama quem e somar o trabalho por nível.
3
Teorema Mestre
Fórmula fechada para uma classe ampla de recorrências.
→ Próximo passo (seção 2): antes de qualquer método, você precisa saber ler uma equação de recorrência — identificar cada parte e entender o que ela representa. Vamos construir isso a partir de um algoritmo que você já conhece.

2 Anatomia de uma recorrência

Vamos construir uma equação de recorrência do zero — a partir de um algoritmo que você já conhece, observando o que acontece em cada chamada.

Passo 1 — observe o que o Merge Sort faz

def merge_sort(arr):
    if len(arr) <= 1:          ← caso base: 1 elemento, custo O(1)
        return arr
    meio = len(arr) // 2
    esq = merge_sort(arr[:meio])   ← chama a si mesmo com n/2 elementos
    dir = merge_sort(arr[meio:])   ← chama a si mesmo com n/2 elementos
    return merge(esq, dir)         ← junta as duas metades: custa n operações

Para um array de n elementos, o Merge Sort faz três coisas:
① Chama a si mesmo duas vezes — uma para cada metade (n/2 elementos cada)
② Junta as duas metades ordenadas — isso custa n comparações
③ Para quando o array tem 1 elemento — custo constante

Passo 2 — escreva o custo em português

"O custo de ordenar n elementos é igual a duas vezes o custo de ordenar n/2 elementos, mais n operações para juntar."

Essa frase é a recorrência. Agora só precisamos de uma notação para escrevê-la de forma compacta.

Passo 3 — o que cada símbolo representa

Cada símbolo abaixo é a versão curta de uma parte da frase que você acabou de ler:

T(n)
"O custo de processar n elementos" — é o que queremos descobrir. Você viu isso em português: "o custo de ordenar n elementos".
T(8) = custo de rodar merge_sort em um array de 8 elementos
2 · T(n/2)
"Duas vezes o custo de processar n/2 elementos" — as duas chamadas recursivas, cada uma com metade do array.
T(8) chama T(4) duas vezes → custo das chamadas = 2 · T(4)
+ n
"Mais o trabalho feito fora das chamadas recursivas" — o merge das duas metades, que custa n comparações. Esse é o custo local, independente da recursão.
T(8): o merge de dois arrays de 4 elementos exige até 8 comparações
T(1) = 1
"Quando n = 1, o custo é constante" — o caso base. Um array de 1 elemento já está ordenado, retorna imediatamente. Sem isso, a recorrência seria infinita.
merge_sort([x]) retorna [x] sem nenhuma comparação

A equação completa

Merge Sort — equação de recorrência
T(n) = 2 · T(n/2) + n
T(n) = custo total para n elementos
2 = duas chamadas recursivas
T(n/2) = custo de cada chamada (metade do array)
n = custo do merge (trabalho local)
T(1) = 1 (caso base)

A forma geral — outros algoritmos, mesmo padrão

O Merge Sort é um caso específico da forma geral T(n) = a·T(n/b) + f(n). Veja o que muda entre algoritmos:

Merge Sort
T(n) = 2T(n/2) + n
● a=2: chama esquerda E direita
● b=2: cada metade tem n/2
● f(n)=n: merge custa n comparações
Busca Binária
T(n) = 1T(n/2) + 1
● a=1: só chama UMA metade
● b=2: a metade relevante tem n/2
● f(n)=1: uma comparação por nível
Erro comum — esquecer o caso base: T(n) = 2T(n/2) + n sem T(1) = 1 não está completa. Sem caso base, a equação se refere a si mesma infinitamente. Toda recorrência precisa de um ponto de parada.
→ Próximo passo (seção 3): você já sabe ler e escrever uma recorrência. Agora vamos resolver — o primeiro método é a expansão: abrir a equação passo a passo até o padrão aparecer.

3 Método 1: Expansão (Unrolling)

Lembra da analogia dos juros compostos? "Quanto vale R$1.000 após 5 anos com 10% ao ano?" Você pode calcular assim:

Ano 1: 1000 × 1.1 = 1100
Ano 2: 1100 × 1.1 = 1210
Ano 3: 1210 × 1.1 = 1331
...
Após k anos: 1000 × 1.1ᵏ

Você substitui o valor do ano anterior pela fórmula, repete, e depois de k passos reconhece o padrão: 1000 × 1.1ᵏ. Isso é expansão.

Com recorrências é o mesmo processo: substituir T(n) pela sua própria definição, uma vez a cada passo. Depois de k substituições você reconhece um padrão geral — e então descobre qual k faz a recorrência "tocar o fundo" (chegar ao caso base T(1)).

O que é "k" aqui?

k é o número de vezes que você abriu a equação. Depois de 1 abertura você tem T(n/2). Depois de 2 você tem T(n/4). Depois de k você tem T(n/2ᵏ). Quando n/2ᵏ = 1, você chegou ao caso base — esse é o k que interessa.

O que procurar em cada expansão

Em toda expansão você precisa encontrar duas coisas:

1. A expressão geral após k aberturas
Uma fórmula que combina k com T no caso base. Ex: T(n/2ᵏ) + k, ou 2ᵏ · T(n/2ᵏ) + k·n.
2. O k que chega ao caso base
Quando n/2ᵏ = 1 → k = log₂n.
Quando n − k = 1 → k = n − 1.
Substitua esse k na expressão geral.

Com T(1) = 1 e o k correto, você tem o custo total em função de n.

Quando usar expansão: funciona bem para recorrências simples (a = 1 ou 2, f(n) constante ou linear). Para recorrências com a ≥ 3 ou f(n) complexo, a álgebra fica pesada — prefira o Teorema Mestre.
→ Próximo passo (seção 4): a expansão é algébrica — você trabalha com fórmulas. O método da árvore de recorrência dá a mesma resposta de forma visual, mostrando exatamente quanto trabalho é feito em cada "camada" de chamadas recursivas.

4 Método 2: Árvore de recorrência

Antes de calcular qualquer coisa, observe o que acontece quando o Merge Sort executa em um array de 8 elementos. Cada chamada recursiva divide o problema — e se você desenhar quem chama quem, vai ver uma árvore se formando.

Você já viu isso em F1.1. A animação do Merge Sort mostrava a árvore de chamadas se revelando nível a nível, com n operações de merge por nível. O método da árvore de recorrência é exatamente isso — mas agora vamos tornar explícito por que cada nível custa n, e por que são log₂(n) níveis.

O que é um "nível"? Nível 0 é a chamada original (n elementos). Nível 1 são as duas chamadas que ela faz (n/2 cada). Nível 2 são as quatro chamadas do nível 1 (n/4 cada). Cada vez que você desce um nível, os problemas ficam menores mas são mais numerosos.

Como construir a árvore — T(n) = 2T(n/2) + n

Cada linha da tabela abaixo corresponde a um nível da árvore. Use o botão "Próximo nível" para revelar nível a nível.

Árvore de recorrência: T(n) = 2T(n/2) + n

Tamanho inicial n =
Níveis de merge — cada um custa n no total
Nível base — arrays de 1 elemento, custo 0

A lógica do método em três passos

1
Calcule o trabalho em cada nível.
Nível 0: 1 chamada com n elementos → merge custa n. Total do nível: n.
Nível 1: 2 chamadas com n/2 elementos cada → merge custa n/2 por chamada → 2 × n/2 = n.
Nível 2: 4 chamadas com n/4 elementos cada → merge custa n/4 por chamada → 4 × n/4 = n.

O padrão: no nível k há 2ᵏ chamadas, cada uma com n/2ᵏ elementos, custando n/2ᵏ para o merge. Total do nível: 2ᵏ × n/2ᵏ = n. Constante por nível — essa é a chave do Merge Sort.
2
Conte quantos níveis há.
O array começa em n e é dividido por 2 a cada nível: n → n/2 → n/4 → … → 1.
Quantas divisões por 2 até chegar em 1? Exatamente log₂(n). (Você viu isso em F1.2: log₂(n) é a quantidade de vezes que você divide n por 2 até chegar em 1.)
No nível final (tamanho 1), não há merge — custo 0.
3
Some o trabalho de todos os níveis.
São log₂(n) níveis de merge, cada um fazendo n trabalho. Total: n × log₂(n) = O(n log n).
Nota: a base do log não importa para Big-O — log₂ e log₁₀ diferem só por uma constante multiplicativa, que some no Big-O.

Quando a árvore fica assimétrica: o método funciona mesmo quando os subproblemas não são iguais (ex: T(n) = T(n/3) + T(2n/3) + n). Nesses casos o Teorema Mestre não se aplica diretamente, mas a árvore ainda pode ser somada — cada nível tem um custo diferente, e você soma uma série geométrica.
→ Próximo passo (seção 5): expansão e árvore são poderosos, mas trabalhosos para recorrências complexas. O Teorema Mestre é uma fórmula fechada — dados a, b e f(n), você identifica qual dos três casos se aplica e lê o resultado diretamente.

5 Método 3: Teorema Mestre

Expansão e árvore funcionam para qualquer recorrência, mas exigem cálculo manual. O Teorema Mestre é diferente: para uma família específica de recorrências da forma T(n) = a·T(n/b) + f(n), ele dá o resultado direto — você identifica três números, consulta três casos, e lê a resposta.

A ideia central é uma competição: quem domina o custo total — o trabalho feito em cada nível (f(n)) ou o número de chamadas que explodem até as folhas? O Teorema Mestre mede exatamente isso.

Dicionário dos símbolos do Teorema Mestre

a ≥ 1
Número de subproblemas por chamada. Deve ser inteiro ≥ 1.
Merge Sort: a = 2 · Busca binária: a = 1 · Strassen: a = 7
b > 1
Fator de redução do tamanho. Cada subproblema tem tamanho n/b. Deve ser > 1 (se b = 1, o tamanho nunca diminui).
Merge Sort: b = 2 · Busca ternária: b = 3
log_b(a)
Quantos níveis a árvore tem até as folhas crescerem por fator a. É o expoente que aparece no custo total das folhas: se você tem a subproblemas por nível e log_b(n) níveis, o número total de folhas é a^(log_b(n)) — que por propriedade de logaritmos é igual a n^(log_b(a)).
a=2, b=2 → log₂(2) = 1  ·  a=4, b=2 → log₂(4) = 2  ·  a=1, b=2 → log₂(1) = 0
n^log_b(a)
Custo total das folhas da árvore de recursão. A árvore tem n^(log_b(a)) folhas; cada folha resolve um subproblema de tamanho O(1). Esse é o "peso" acumulado das chamadas recursivas — o adversário que f(n) precisa vencer.
Merge Sort: a=2, b=2 → n^(log₂2) = n¹ = n  ·  Strassen: a=7, b=2 → n^(log₂7) ≈ n^2.81
f(n)
Custo do trabalho local em cada chamada (além das recursões). É comparado com n^(log_b(a)) para decidir quem domina.
Merge Sort: f(n) = n · Busca binária: f(n) = 1 · Strassen: f(n) = n²

A comparação central: f(n) vs n^log_b(a)

O TM pergunta: quem cresce mais rápido?

TRABALHO LOCAL
f(n)
vs
CUSTO DAS FOLHAS
nlogba

O resultado é dominado pelo maior dos dois. Se empatar, multiplica por log n.

Antes dos três casos: o que é ε?

ε (épsilon) é um número positivo, por menor que seja. Nos casos 1 e 3, a condição não exige que f(n) seja um pouco menor ou maior que n^(log_b(a)) — exige que seja polinomialmente diferente. "f(n) = O(n^(log_b(a) − ε))" significa: f(n) cresce como n elevado a um expoente que é estritamente menor que log_b(a), mesmo que por uma margem ínfima. Isso exclui o caso de empate (que é o Caso 2). Na prática, você raramente calcula ε explicitamente — você compara os expoentes e verifica se há diferença polinomial.

Os três casos

1
Folhas dominam
f(n) = O(n^(log_b(a) − ε))
para algum ε > 0
T(n) = Θ(n^log_b(a))
f(n) cresce mais devagar que n^log_b(a). As folhas da árvore custam mais que a raiz. O custo é dominado pelas folhas.
2
Empate
f(n) = Θ(n^log_b(a))
(mesmo crescimento)
T(n) = Θ(n^log_b(a) · log n)
f(n) e n^log_b(a) crescem igual. Cada um dos log n níveis contribui igualmente. O log n extra vem dos log n níveis somados.
3
Raiz domina
f(n) = Ω(n^(log_b(a) + ε))
para algum ε > 0 (+ cond. regularidade)
T(n) = Θ(f(n))
f(n) cresce mais rápido que n^log_b(a). O trabalho da raiz domina. O custo total é determinado pela chamada de nível 0.

Fórmula anotada

Teorema Mestre — forma geral
T(n) = a · T(n/b) + f(n)
a = nº de subproblemas
b = fator de redução
f(n) = trabalho local
n^log_b(a) = custo das folhas
Caso 1: folhas > raiz → Θ(n^log_b(a))
Caso 2: empate → Θ(n^log_b(a) · log n)
Caso 3: raiz > folhas → Θ(f(n))

Quando o TM NÃO se aplica:
● T(n) = T(n−1) + 1 — redução é n−1, não n/b. TM exige divisão por b > 1.
● T(n) = T(n/2) + n·log n — f(n) não é polinomial puro; o log n extra impede a comparação direta (use expansão ou variante do TM Estendido).
● T(n) = T(n/2) + T(n/3) + n — dois subproblemas de tamanhos diferentes; não tem a forma a·T(n/b).

6 Exemplos resolvidos

Exemplo A — Busca binária: T(n) = T(n/2) + 1

Dois métodos, mesma resposta.

Via Expansão:

T(n) = T(n/2) + 1     (abertura 1)
= T(n/4) + 1 + 1  (abertura 2: T(n/2) → T(n/4)+1)
= T(n/8) + 1 + 1 + 1  (abertura 3)
...
= T(n/2ᵏ) + k     (após k aberturas: k somas de 1)
Quando n/2ᵏ = 1 → k = log₂n
T(n) = T(1) + log₂n = 1 + log₂n

Via Teorema Mestre:

a=1, b=2, f(n)=1
log_b(a) = log₂(1) = 0
n^0 = 1 = f(n)
→ Caso 2 (empate)
T(n) = Θ(n⁰ · log n) = Θ(log n)
Resultado: O(log n) — confirmado pelos dois métodos. Para n = 1.000.000, isso significa ≈ 20 comparações.

Exemplo B — Merge Sort: T(n) = 2T(n/2) + n

1
Identificar: a=2, b=2, f(n)=n
2
Calcular: log₂(2) = 1, portanto n^log_b(a) = n¹ = n
3
Comparar: f(n) = n = n^log_b(a) = n → Caso 2 (empate)
4
Aplicar: T(n) = Θ(n¹ · log n) = Θ(n log n)
Confirma o que você viu na árvore em F1.1: log₂(n) níveis × n por nível = n log n.

Exemplo C — Recursão ingênua: T(n) = 2T(n−1)

Aparece no cálculo ingênuo de Fibonacci e na solução recursiva ingênua da Torre de Hanói.

⚠ O TM não se aplica aqui — a redução é n−1, não n/b.

Via Expansão:

T(n) = 2T(n−1)
= 2 · 2T(n−2) = 2²T(n−2)
= 2³T(n−3)
= 2ᵏT(n−k)
Quando n−k=1 → k = n−1
T(n) = 2^(n−1) · T(1) = 2^(n−1)
Resultado: O(2ⁿ) — exponencial. Para n=50 isso é ~10¹⁵ operações. Por isso memoização/programação dinâmica é essencial para Fibonacci.

Exemplo D — Insertion Sort pior caso: T(n) = T(n−1) + n

A cada chamada você insere 1 elemento na posição certa em uma lista já ordenada — no pior caso isso custa n comparações.

⚠ TM não se aplica (redução n−1). Use expansão.

T(n) = T(n−1) + n
= T(n−2) + (n−1) + n
= T(n−3) + (n−2) + (n−1) + n
= T(1) + 2 + 3 + ... + n
Por que T(1) + 2 + 3 + ... + n? A cada abertura você descola um termo: primeiro n, depois n−1, depois n−2, até chegar em T(1) com os termos 2, 3, ..., n acumulados. É a soma dos inteiros de 2 até n, que é a mesma coisa que (soma de 1 a n) − 1.

Soma de 1 a n = n(n+1)/2  (fórmula de Gauss: n termos, média (1+n)/2, produto = n(n+1)/2)
Portanto: T(1) + 2 + 3 + ... + n = 1 + [n(n+1)/2 − 1] = n(n+1)/2
Resultado: O(n²) — quadrático. Confirma o que se sabe sobre Insertion Sort no pior caso (array invertido).

8 Resumo

🎯 O que você precisa dominar

Uma recorrência tem três partes: chamadas recursivas a·T(n/b), trabalho local f(n), e caso base T(1)
Expansão: substitua T(n) repetidamente, encontre o padrão geral e qual k toca o caso base
Árvore de recorrência: some o trabalho por nível — nós × custo por nó. Para T(n)=2T(n/2)+n dá n × log₂n
Teorema Mestre: calcule n^log_b(a), compare com f(n), aplique Caso 1, 2 ou 3
TM não se aplica quando a redução é n−1 (não n/b) ou quando f(n) tem log extras não-polinomiais
T(n) = 2T(n−1) → O(2ⁿ); T(n) = T(n−1)+n → O(n²) — recursão linear não é sempre barata
Merge Sort e busca ternária têm o mesmo estrutura de TM (Caso 2) — o resultado é sempre Θ(n^log_b(a) · log n)
